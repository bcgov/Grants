Redis in the Unity bridge

How the Applicant Portal reads, writes, and reconciles Unity Grant Manager data through a Redis cache sitting between two very different integration paths — a synchronous REST read, and an asynchronous, queued write with its own ack/nack loop.

01 The two lanes

Two ways in, one cache in the middle

Everything the Unity plugin does falls into one of two shapes, and Redis plays a different role in each.

Reads — providers, contacts, addresses, organizations, submissions, payments — go straight to Unity's single /api/app/applicant-profiles/profile endpoint the first time, and to Redis every time after that.

Writes — create/edit/delete a contact or address, set either as primary, edit the organization — never call Unity synchronously at all. The plugin patches Redis, drops a command in a transactional outbox, and a background job ships it to RabbitMQ. Unity confirms later, asynchronously.

ReadsWrites
Synchronous REST call on a missAsynchronous — outbox + RabbitMQ
Redis: source of truth once warmRedis: optimistic guess, unconfirmed
Cache written by the read itselfCache written before Unity even sees the command
No compensation neededCompensated on FAILED / timeout — see §06

Why UNITY does it the hard way

The plugin system ships a second implementation — DEMO — as a self-contained mock. Comparing the two is the fastest way to see exactly what the outbox/inbox machinery buys UNITY:

DEMOUNITY
Write pathDirect — in-memory store, then RedisOptimistic — patch Redis, then queue a command
External systemNoneReal Unity instance over RabbitMQ
Ack / nack round-trip?Not needed — writes are synchronousFull round-trip via the inbox
Can a write silently fail later?NoYes — that's exactly what §06 compensates for

The asymmetry is the point: DEMO can afford a direct write because it is the source of truth. UNITY isn't — Unity Grant Manager is — so every optimistic patch is a promise that has to be either confirmed or walked back.

02 Reads

Reading profile data: cache-aside, on demand

Every read-shaped call funnels through UnityPlugin.PopulateProfileAsync, which delegates entirely to a shared, plugin-agnostic IPluginCacheService.GetOrFetchAsync.

  1. Build the cache segment from the request: {Provider}:{Key} — e.g. DGP:CONTACTINFO.
  2. Check Redis for that key first. A hit deserializes, stamps CacheStatus: HIT for diagnostics, and returns — no network call to Unity at all.
  3. A corrupt or null cache entry is logged, evicted, and treated as a miss rather than surfaced to the caller — the read never fails just because the cache went bad.
  4. On a genuine miss, call Unity's REST endpoint with TenantId, Key, ProfileId, Subject; strip the internal dataType wrapper; store the result in Redis with the configured TTL before returning it.
cache key format
pattern{CacheKeyPrefix}{profileId}:{pluginId}:{provider}:{key}
exampleprofile:019b4788-…:UNITY:DGP:CONTACTINFO

One exception: SUBMISSIONFORMDATA (the PDF source data) goes through the same cache-aside method but is fetched on-demand only — never pre-seeded like the rest — and scoped per submission ID, so it adds one cache entry per submission a user actually opens, not per profile load.

03 Writes, part 1

Commands that update the cache: patch first, ask later

Every write endpoint — create/edit/delete a contact or address, set either as primary, edit the organization — runs the same two-step pattern before Unity is even told:

  1. Patch the cached JSON in place. PatchCachedProfileDataAsync reads the current cache, applies a targeted transform, and writes it back — a no-op if nothing's cached yet, so it never fabricates a segment from nothing.
  2. Fire the matching command onto the outbox (§04). The handler returns success to the caller immediately — the applicant sees their edit in the UI before Unity has even received it.
OperationCache patchPrimary-flag rule
Contact createAppend to contacts[]New primary clears isPrimary on the rest
Contact editReplace in contacts[]Same as create, on the new value
Contact set-primaryToggle across contacts[]Target → true, everyone else → false
Contact deleteRemove from contacts[]If it was primary, auto-promote the most recent remaining contact
Address create / editAppend / replace in addresses[]Only addresses of the same type are demoted
Address set-primaryToggle within the type groupOther address types keep their own primary untouched
Address deleteRemove from addresses[]Auto-promotes within the same type group only
Organization editPatch the OrganizationInfo object—
 
// Unity.Addresses.cs — CreateAddressAsync (abbreviated)
var newAddressId = Guid.NewGuid();

// STEP 1: update cache optimistically
await UpdateAddressCacheOptimistically(newAddressId, addressRequest, ctx, ct);

// STEP 2: fire the command — same IsPrimary the cache was patched with,
// so the flag survives the next hydration from Unity
await FireAddressCreateMessage(newAddressId, addressRequest, ctx, ct);

return Result<Guid>.Success(newAddressId);

A smaller guard worth knowing about: when a new address's type group has no flagged primary yet, the plugin promotes it before patching — otherwise the next read would infer a primary anyway, and the inferred one would silently lose that status the moment a newer address in the same group arrived.

Self-healing by design

The cache is only ever an optimistic guess. When its TTL lapses — 60 min absolute / 15 min sliding, configured — the next read is a guaranteed miss, which re-fetches from Unity and reconciles any drift. Even without a single failure or nack, the system corrects itself on a clock.

Answering "what's primary now?" without asking Unity

An address mutation endpoint has to return the applicant's current primaries in its response — and it does that by reading the same optimistically-patched cache back, via PrimaryAddressResolver, never by calling Unity. One applicant can hold one primary per address type, so the resolver groups by type and, within each group:

  1. The address explicitly flagged isPrimary: true wins.
  2. If none is flagged, the most recently created address in that group is inferred as primary.
  3. If nothing has a creationTime either, it falls back to the first address in the group.

This is exactly why §03's patch routines always write isPrimary: false explicitly on the addresses they demote — even when the cached entry didn't carry the property at all. A test locks this in: CreateAddress_WritesIsPrimaryFalse_EvenWhenTheCachedEntryLacksTheProperty. Skip that write and step 1 above finds no flagged winner, falls through to inference, and a stale entry can end up "primary" again by accident.

04 Writes, part 2

Sending the command to Unity

The fire step wraps the change as a PluginDataMessage and hands it to IMessagePublisher, which writes a Pending row to the transactional OutboxMessage table — in the same request, not to RabbitMQ directly.

{
  "messageId": "f6a7b8c9-d0e1-2345-f012-3456789abcde",
  "messageType": "PluginDataMessage",
  "correlationId": "profile-019b4788-d7a7-7c40-b25e-98a361adbbfc",
  "pluginId": "UNITY",
  "dataType": "ADDRESS_SET_PRIMARY_COMMAND",
  "data": {
    "action": "SetAddressAsPrimary",
    "addressId": "BBD12E34-6789-0ABC-DEF1-234567890ABC",
    "profileId": "019b4788-d7a7-7c40-b25e-98a361adbbfc",
    "provider": "DGP",
    "subject": "Abad@idir"
  }
}

OutboxProcessorJob polls every 30s, publishes to exchange grants.messaging with routing key commands.unity.plugindata, and sets the AMQP MessageId to the outbox row's own MessageId — the value Unity is expected to echo back in its acknowledgment so the two sides can be joined.

That routing key isn't configured anywhere — it's derived, every time, from the message itself:

// GenerateRoutingKey(messageType, pluginId)
prefix = pluginId.ToLowerInvariant();                 // "unity"
suffix = messageType.ToLowerInvariant()
                     .Replace("message", "");          // "PluginDataMessage" → "plugindata"
return $"commands.{prefix}.{suffix}";                  // "commands.unity.plugindata"

Which is also why .MessageType conventionally ends in …Message across the codebase — PluginDataMessage, MessageAcknowledgment is the deliberate exception (it ends in the un-suffixed grants.{plugin}.acknowledgment pattern instead, generated by the ack publisher, not this job). Add a new command type and its routing key just falls out — no registry entry required.

05 A layer most people skip past

Transport-level ack/nack: not the same ack/nack

"Ack/nack" actually happens twice, at two unrelated layers, and it's easy to conflate them. §06 covers the business one — Unity's SUCCESS/FAILED verdict on a command it already received. This layer is lower: the AMQP protocol's own BasicAck/BasicNack, decided by RabbitMQConsumer the instant any message — command or acknowledgment — arrives off the wire, before a single byte of it has been interpreted as a plugin message.

The consumer runs with prefetchCount: 1 (one message in flight at a time, no pipelining) and autoAck: false — it decides deliberately, every time:

ConditionBroker callEffect
Body exceeds MaxMessageSizeBasicNack(requeue: false)Dropped — a malformed giant payload can't loop forever
Body isn't valid JSONBasicNack(requeue: false)Dropped — redelivering unparseable bytes would never succeed
Stored as InboxMessage successfullyBasicAckRemoved from the queue — durably ours now, InboxProcessorJob takes it from here
Inbox write fails (e.g. DB unavailable)BasicNack(requeue: true)Put back on the queue for redelivery
Any other unexpected exceptionBasicNack(requeue: true)Put back — assumed transient

Duplicate protection lives one layer up from this, deliberately: _inboxRepository.AddAsync checks MessageId before the row is written, so a message redelivered after a requeue — or a genuine duplicate from Unity — is recognized and doesn't get processed twice by InboxProcessorJob. The AMQP layer's only job is "did this arrive intact," not "have I seen this before."

Worth a question in the room

The requeue-on-failure path has no visible cap or dead-letter routing in this consumer's own setup. If the database were down long enough, a message could requeue and redeliver indefinitely rather than eventually landing somewhere for manual inspection. Worth confirming whether a dead-letter exchange or TTL is configured on the queue itself (outside this code) to bound that.

06 Closing the loop

Business-level ack / nack and cache invalidation

Once a message clears the transport layer above, InboxProcessorJob (every 15s) reads its payload to find out what Unity actually said. For a MessageAcknowledgment — routing key grants.unity.acknowledgment — the status is SUCCESS, FAILED, or PROCESSING:

Ack statusOutbox effectCache effect
SUCCESS Marked Acknowledged None — the optimistic patch from §03 was correct
FAILED Marked Acknowledged, PluginEvent recorded (InboxRejection) Invalidated — the exact segment the command touched
PROCESSING Logged, left untouched None — waiting for a final answer
no ack in 5 min Marked TimedOut, PluginEvent recorded (AckTimeout) Invalidated — same compensation as a FAILED ack

The cache segment to clear isn't guessed — it's resolved from the command's own dataType via UnityCommandMetadataProvider.GetCacheSegment(), e.g. ADDRESS_EDIT_COMMAND → ADDRESSINFO. The next read for that profile/provider is a guaranteed miss, so it goes back to Unity for the truth instead of continuing to serve the guess that turned out wrong.

Late-ack safety

If Unity's ack shows up after the timeout job already fired, it's still processed — TimedOut → Acknowledged is a valid transition. The cache was already invalidated by the timeout, so the late answer can't re-confirm stale data; the next read simply fetches fresh state either way.

On the user-visible side, every recorded event shows up at GET /Events/UNITY/{Provider} with a friendly message built from the same metadata provider (e.g. "address update" for ADDRESS_EDIT_COMMAND), and the applicant can dismiss it via the acknowledge endpoints. The message is deliberately soft — "…your data may revert on next refresh" — because that's exactly what just happened.

07 The gate

Upfront validation: nothing touches the cache until it passes

FastEndpoints runs the request's FluentValidation validator before HandleAsync ever executes. A bad request never reaches the plugin — it never patches Redis, and it never gets queued to Unity. Validation is the only gate in the entire pipeline; nothing downstream re-checks the shape of the data before it's optimistically written and published.

public class UpdateAddressValidator : Validator<UpdateAddressRequest>
{
  public UpdateAddressValidator()
  {
    RuleFor(x => x.AddressId).NotEmpty();
    RuleFor(x => x.AddressType).NotEmpty().MaximumLength(50);
    RuleFor(x => x.Street).NotEmpty().MaximumLength(200);
    RuleFor(x => x.City).NotEmpty().MaximumLength(100);
    RuleFor(x => x.Province).NotEmpty().MaximumLength(50);
    RuleFor(x => x.PostalCode).NotEmpty().MaximumLength(20);

    // Required exactly as on Create: HandleAsync forwards this straight into
    // EditAddressCommand, and the Unity plugin publishes it in
    // ADDRESS_EDIT_COMMAND — an omitted value would send Guid.Empty downstream
    // rather than being resolved from the authenticated profile.
    RuleFor(x => x.ApplicantId).NotEmpty();
  }
}
Why this one rule matters

Skip the ApplicantId check and Guid.Empty doesn't just fail quietly — it gets written into the optimistic cache patch and published to Unity inside ADDRESS_EDIT_COMMAND, because nothing between the endpoint and the outbox re-validates it. Upfront validation isn't a formality here; it's the only place this class of bug can be caught before it becomes visible state in two systems.

09 Under the hood

What keeps the two background jobs from tripping over each other

OutboxProcessorJob and OutboxTimeoutJob both run on every pod, on their own Quartz schedule, with [DisallowConcurrentExecution] guarding each job against overlapping itself — but nothing stops two pods from firing the same job at the same moment. Three mechanisms handle the rest:

MechanismWhat it prevents
Distributed lock per job key (outbox-processor, outbox-timeout), 5-minute duration, renewed every 2 minutes mid-batchTwo pods processing the same batch of pending/timed-out messages at once
Job circuit breaker — ShouldExecute gates the whole run; failures back off 15s → 30s → 60s → 120s → 300s (capped)A down Redis or Postgres turning into a tight retry loop and a flood of identical error logs
Status re-check on the timeout path — GetCurrentStatusAsync reads straight from the database (no tracked entity) immediately before compensatingThe race below

That third one is the subtle case worth walking through out loud: OutboxTimeoutJob loads a batch of messages that were Published and older than the cutoff — but between that load and actually acting on a given message, InboxProcessorJob could process a genuine late ack for the very same message on another pod. Without a re-check, the timeout job would invalidate a cache segment that the ack had just correctly left alone (or double-invalidate one already handled). The guard is one extra untracked read:

// OutboxTimeoutJob.ProcessTimedOutMessage
var currentStatus = await _outboxRepository.GetCurrentStatusAsync(message.Id, ct);
if (currentStatus != OutboxMessageStatus.Published)
{
    // an ack landed concurrently — this message isn't ours to time out
    return;
}

It's a small guard, but it's the difference between "the ack/nack loop is eventually consistent" and "the ack/nack loop is eventually consistent, except during the exact window two jobs are both looking at the same row."

TBD · proposed, not yet built

Server-initiated invalidation: let Unity tell us when to forget

Every invalidation covered so far is reactive — it fires in response to something the Portal itself did (a write that came back FAILED, or timed out). There's no path today for Unity to say "something changed on my side, independent of anything you asked for" — a case worker edits the applicant's contact info directly inside Unity, say, with the Portal never involved. The proposal: let Unity publish a lightweight event for exactly that, and treat it the same way §06 already treats a failed ack — just invalidate.

The extension point already exists and is already shaped for this. UnityPluginMessageHandler.HandleIncomingDataAsync — the same method routed to by the transport in §05/§06 — already has stub cases for this exact shape of message (PROFILE_UPDATE, STATUS_UPDATE), each currently just a log line and a // TODO. This proposal is about filling one of those in for real, not building new plumbing.

The core insight

This isn't a "refresh on login" feature. It's one delete. Because every profile read is already cache-aside (§02), invalidating a segment is enough — the next time anything reads it, that read is a guaranteed miss and re-fetches from Unity. In practice that next read happens shortly after the applicant's next login, when the frontend re-populates their contacts/addresses/etc. — so "updated info on next login" is a consequence of existing behavior, not a new code path to build.

Open questions before this gets built:

  • What does Unity actually send — a specific segment that changed (e.g. CONTACTINFO only), or a profile-level "something changed, refresh everything"?
  • IDistributedCache has no wildcard or pattern delete. A profile-level event can't invalidate "everything for this profile" in one call — it has to loop a fixed list of known segments (CONTACTINFO, ADDRESSINFO, ORGINFO, SUBMISSIONINFO, PAYMENTINFO) via IProfileCacheInvalidationService, one call per segment.
  • What's the dataType and payload shape? Reuse the already-stubbed PROFILE_UPDATE / STATUS_UPDATE, or define a dedicated CACHE_INVALIDATE — and does the payload carry profileId + provider the same way every outbound command already does?
  • Should it raise anything user-visible? Wiring it through PluginEventService.RecordAsync (§06) at Info severity — "your information was recently updated" — costs one call, but a silent invalidation may be the better UX for a change the applicant didn't initiate themselves.
  • No new infrastructure is needed on the routing side — Unity publishes to the same exchange with a routing key like grants.unity.datachange, which the Portal's existing grants.*.# queue binding already picks up.

For the room

Discussion prompts

  • The code-level cache TTL default (30 min / 10 min) and the shipped config (60 min / 15 min) disagree — is that split intentional per environment, or should the class default match production?
  • UnityPluginMessageHandler's SUCCESS and PROCESSING branches are still logging-only stubs (// TODO: update cache, notify user, etc.) — anything Unity-specific worth adding beyond what the generic inbox path already does?
  • A PROCESSING ack is currently a no-op — should it push out the ack-timeout window for genuinely long-running commands, instead of racing the same 5-minute clock?
  • Late acks are handled safely today because the cache was already invalidated by the timeout — worth confirming Unity's own retry/redelivery semantics can't produce a late ack for a command it's also about to retry.
  • The AMQP-level requeue-on-failure path (§05) has no visible cap in this consumer — is there a dead-letter exchange or TTL configured on the queue itself to stop an indefinite requeue loop during a prolonged database outage?
  • The transport-level ack (§05) and the business-level ack (§06) are easy to conflate in conversation — is it worth renaming one of them in code or docs (e.g. "delivery ack" vs "processing ack") to keep them distinct when this comes up in incident reviews?
  • For the proposed push-invalidation event (TBD) — does Unity have a reliable trigger point to publish it from (e.g. a save handler in their own UI), or would it need polling/change-detection on their side that doesn't exist yet?
  • If the answer above is "profile-level, not granular," is looping five known segments per event acceptable, or does it push us toward giving IPluginCacheService an actual pattern-delete (which means moving off the generic IDistributedCache abstraction toward something Redis-specific)?
