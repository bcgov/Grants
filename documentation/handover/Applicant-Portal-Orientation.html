01 Orientation

What the Applicant Portal is — and what it deliberately isn't

The Applicant Portal is the applicant-facing half of BC Government grants administration. An applicant signs in with a BC Gov identity, sees the grant submissions they've made, tracks status, keeps their own contact and address details current, and views payments. Staff-side grant administration is not here — that lives in Unity Grant Manager, a separate system owned by another team.

That split is the single most important thing to internalise, because it explains most of the architecture:

The Portal ownsUnity owns
The applicant's login-to-profile mapping (Profile)Applicants, applications, submissions, payments — the real records
Messaging state — outbox, inbox, plugin eventsThe authoritative answer to "is this data valid?"
A cache of Unity's answers, in RedisWhether a write the Portal sent actually succeeded
The UI, and the rules about what a user may seeBusiness rules about grants themselves

So the Portal is mostly an integration and presentation layer over someone else's system of record. It has a database, but almost nothing applicant-visible lives in it. When you catch yourself asking "where is this stored?", the answer is usually "it isn't — we asked Unity and cached the reply."

The one idea to carry forward

Reads from Unity are synchronous and cached. Writes to Unity are asynchronous and optimistic — the Portal updates its cache, tells the user "done," and only finds out later whether Unity agreed. Nearly everything that looks like unusual complexity in the backend exists to make that safe.

03 The path

One request, end to end

Follow a single realistic action — an applicant edits their mailing address — and you'll have touched nearly every layer in the system. This is the walkthrough worth doing on day one with the files open beside you.

The same path, as a checklist of files

  1. Route guard. core/guards/auth.guard.ts keeps unauthenticated users out; they land on /login, which starts the Keycloak OIDC redirect.
  2. The call. The component calls a typed method on api.service.ts — never HttpClient directly. core/interceptors/auth.interceptor.ts adds Authorization: Bearer <token>.
  3. Getting to the API. Locally the Angular dev server proxies /api; in a container server.js does it when ENABLE_API_PROXY=true.
  4. Middleware. The order lives in one file — API.Web/Configurations/MiddlewareConfig.cs. Its last step, ProfileResolutionMiddleware, turns the JWT into a Portal Profile and stashes it on HttpContext.Items.
  5. Endpoint. API.Web/Addresses/. It validates, reads the profile via GetRequiredProfile(), dispatches through MediatR, and maps the Result to a status code. No business logic.
  6. Handler. API.UseCases/Addresses/…. Owns the logic, returns Result<T>, and reaches the outside world through an interface — it doesn't know Unity exists.
  7. Plugin. API.Plugins/Unity/. Patches the Redis segment, writes an outbox row, returns success. Background jobs take it from there.
Where profile resolution bites

ProfileResolutionMiddleware deliberately swallows its own failures — it logs and continues without a profile rather than failing the request. A handler that assumes a profile is present therefore fails further downstream, with a much less obvious error. Read the profile through GetRequiredProfile() so the failure is explicit and close to the cause.

04 Conventions

Backend: four patterns explain almost everything

1 · FastEndpoints, not controllers

There is no MVC controller anywhere. Each endpoint is a class in API.Web/<Domain>/, and it arrives as a set of four files:

FileContains
<Action>.csThe endpoint — route, auth policy, summary, and a single _mediator.Send()
<Action>.Request.csRequest record, including the Route constant
<Action>.Response.csResponse record
<Action>.Validator.csFluentValidation rules — run automatically, before the handler

2 · CQRS through MediatR

Endpoints dispatch; handlers decide. Commands and queries live in API.UseCases/<Domain>/<Action>/ next to their handler. Business logic inside an endpoint class is a bug in the making, not a shortcut.

3 · Result<T> everywhere

Handlers don't throw for expected failures and don't return HTTP concerns. They return an Ardalis Result<T>, and the endpoint translates it:

result.IsSuccess         -->  200 / 201 with result.Value
ResultStatus.NotFound    -->  SendNotFoundAsync()
ResultStatus.Forbidden   -->  SendForbiddenAsync()
ResultStatus.Invalid     -->  AddError() + SendErrorsAsync(422)
result.Errors.Any()      -->  AddError() + SendErrorsAsync(400)

4 · Validation is the only gate

Worth stating plainly, because it has bitten people: nothing downstream re-validates the shape of a request. A value that clears the validator is written into the optimistic cache patch and published to Unity as-is. The validator isn't ceremony — it's the boundary.

Auth default

Authenticated endpoints use the RequireAuthenticatedUser policy; the named constants live in API.Web/Auth/AuthPolicies.cs. Anonymous endpoints are the exception and should be obviously so — health, plugin discovery, the OAuth callback.

05 Conventions

Frontend: standalone components and one import rule

Angular 20, standalone components throughout — no NgModule for features. Routes in app.routes.ts lazy-load with loadComponent. Styling is the BC Gov Bootstrap 5 theme plus SCSS.

FolderHoldsMay import
core/Services, guards, interceptors, auth config, models — the business logiccore, shared
features/One folder per page area: applicant-info, payments, workspace, submission-print, authcore, shared, its own feature
shared/Reusable presentational components, directives, typesshared only
layout/App shell — header, footer, navigationcore, shared

The rule that keeps this honest: core and shared never import from features. If a shared component seems to need feature knowledge, that knowledge belongs in a core service or an input, not an import.

If you change a data-cy attribute

The Cypress suite selects on data-cy attributes through a shared registry (cypress/selectors/registry.ts). Renaming one silently breaks E2E specs that no local test run will catch, because those specs target deployed environments. Run /sync-selectors after touching them.

06 The seam

Plugins: how the Portal stays ignorant of Unity

No handler references Unity. External systems sit behind a plugin abstraction, resolved at runtime from PluginRegistry — initialised once at startup in MiddlewareConfig, which logs how many plugins are registered, configured, and enabled. Two ship today:

PluginWhat it isWhy you care
DEMOA self-contained mock — an in-memory store that is its own source of truthLets you develop and demo the whole portal with no external dependency, and it's the clean reference for what the abstraction actually requires
UNITYThe real integration — REST reads, queued writes, ack/nack, cache compensationEvery piece of apparent complexity in the messaging layer exists for this plugin

Almost every route is shaped /<Domain>/{PluginId}/{Provider}/…. Two identifiers, two different jobs:

PluginId
Which integration to route through — UNITY or DEMO.
Provider
Which grant program or tenant within that system, e.g. DGP. Discovered per plugin via GET /Plugins/{PluginId}/providers.
Read this next, seriously

How the UNITY plugin reads, writes, caches, and reconciles is covered in depth in the companion briefing, Redis in the Unity bridge. It's the other half of this document. Come back to it once the material above feels familiar — most bugs that reach the team live in the territory it describes.

dotnet ef migrations add <Name> \
  --project src/Grants.ApplicantPortal.API.Migrations \
  --startup-project src/Grants.ApplicantPortal.API.Web
Two setup steps that aren't optional

Secrets. The Keycloak client secret and connection strings are never in source control — user secrets locally, environment variables in deployed environments. Work through Secrets Management before your first run, or authentication simply won't initialise.

A token for API testing. To call protected endpoints outside the browser you need a real JWT for your own IDIR/BCeID account — the client-credentials flow will not work for this client. Getting Keycloak Tokens walks through the browser-based authorization code flow.

Migrations and seeding on startup are both configuration-gated (Database:RunMigrationsOnStartup, Database:SeedDataOnStartup). In Development, with migrations off, startup falls back to EnsureCreated — which is why a dev database can exist with no migration history.

The E2E trap

Cypress specs run against dev, dev2, test, uat, or prod — never your local stack. A green local build tells you nothing about whether you broke a spec, and a spec failure can reflect environment data rather than your change. Check CONTRIBUTING.md before weakening any assertion: some are deliberately strict, such as payments data being required in non-production login flows.

09 Process

Shipping a change

Branches flow dev → test → main. Every branch and commit carries its Azure Boards ticket number, so history stays traceable to the work item.

Kind of changeBranchBase
Feature / enhancementfeature/AB#<ticket>-<short-slug>dev
Bug fixbugfix/AB#<ticket>-<short-slug>dev
Hotfixhotfix/AB#<ticket>-<short-slug>test or main

Commit messages start with the ticket: AB#12345 add address validation. Keep changes small and focused, and prefer explicit assertions over broad waits when you touch tests — both are house rules from CONTRIBUTING.md.

Code quality is tracked in SonarCloud, which analyses branches and pull requests; the SonarCloud guide covers what gates a PR and how to read a report.

10 Vocabulary

Words this team uses precisely

Most onboarding confusion is vocabulary, not architecture. These all mean something specific here:

Profile
The Portal's own record of a signed-in applicant, created on first authenticated request by ProfileResolutionMiddleware. It is not the applicant's grant data.
ProfileId
The Portal-side GUID for that profile. Every cache key is scoped by it.
Subject
The OIDC sub (with its issuer) identifying the login itself. One real applicant can have several — see the applicant-merging note in the Unity integration doc.
Provider
A grant program or tenant inside the external system, e.g. DGP.
Segment
One slice of cached profile data: CONTACTINFO, ADDRESSINFO, ORGINFO, SUBMISSIONINFO, PAYMENTINFO. Caching, invalidation, and compensation all work per segment.
dataType
A message's own type discriminator, e.g. ADDRESS_EDIT_COMMAND. It's also what maps a failed command back to the segment that must be invalidated.
Outbox / Inbox
Postgres tables that give transactional guarantees around RabbitMQ: outbound commands are written in the request's transaction and shipped by a job; inbound messages are stored durably before being processed.
PluginEvent
A recorded, user-surfaceable occurrence — typically "a write you made didn't stick." Applicants see these and can dismiss them.
AutoUI
The Cypress E2E suite. Never a local test run.

Hard-won

Things that surprise people in week one

  • A successful write doesn't mean Unity accepted it. The 200 means "cached and queued." Confirmation, or compensation, happens seconds to minutes later.
  • Stale data is often correct behaviour. The cache is an optimistic guess with a TTL; a read that looks wrong may be a patch that was never confirmed. Redis Commander plus the plugin-events endpoint usually tells the story faster than a debugger.
  • Nothing re-validates after the validator. If a bad value reaches the plugin, it reaches both Redis and Unity.
  • Profile resolution fails quietly. Missing-profile symptoms appear downstream, not at the middleware that caused them.
  • Class defaults and shipped configuration disagree in places — cache TTLs being the known case. appsettings.json wins at runtime, so don't reason from the C# default alone.
  • "Ack" is two unrelated things. AMQP delivery acks and Unity's business verdict on a command are different layers. Say which you mean, especially in incident reviews.
  • E2E specs can't be validated locally. Selector changes are the classic silent breakage.
  • The Portal trusts Unity's scoping. Ownership checks confirm that an id appears in what Unity returned for the caller — which makes Unity's applicant-merging behaviour part of the Portal's trust boundary.
